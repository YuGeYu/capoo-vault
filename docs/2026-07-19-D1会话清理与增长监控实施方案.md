## 3. 已确认的代码原因

### 3.1 过期 session 只被动删除

`src/worker.js` 的 `requireOptionalSession()` 当前流程：

1. 从 Cookie 取 token。
2. 查询 `sessions.token_hash`。
3. 如果该 Cookie 对应 session 已过期，删除这一条。
4. 没有再次携带旧 Cookie 的过期 session 永远不会被清理。

这解释了当前 142 条过期记录。

### 3.2 每次有效登录请求都会写 D1

当前查询没有返回 `s.last_seen_at`，随后无条件执行：

```sql
UPDATE sessions SET last_seen_at = ? WHERE id = ?
```

因此同一用户在短时间加载 bootstrap、个人中心、作品详情或后台接口时，会重复更新同一行。

### 3.3 ISO 时间格式注意事项

当前 `expires_at`、`last_seen_at` 使用 JavaScript `toISOString()` 格式，例如：

```text
2026-07-19T02:42:41.631Z
```

SQLite `CURRENT_TIMESTAMP` 通常返回：

```text
2026-07-19 02:42:41
```

二者的空格、`T`、毫秒和 `Z` 不同。直接把文本列与 `CURRENT_TIMESTAMP` 比较可能在同一天产生错误的字典序结果。因此代码和手工 SQL 都要使用同格式 ISO/RFC3339 截止值。

## 4. 最终设计

### 4.1 每日 Cron

在 `wrangler.production.toml` 增加：

```toml
[triggers]
crons = ["15 19 * * *"]
```

Cloudflare Cron 使用 UTC。`19:15 UTC` 对应上海时间次日 `03:15`，即每天凌晨低峰执行。

官方行为需注意：

- Cron 配置最多约 15 分钟传播。
- Wrangler 部署时，配置文件中的 `crons` 会替换已有 Cron 列表。
- 当前仓库没有 Cron 配置或 `scheduled` handler；实施前仍需在 Cloudflare 控制台/当前部署中确认没有用户后来新增的触发器。

Worker 导出结构改为同时支持 fetch 和 scheduled：

```js
export default {
  async fetch(request, env) {
    // 保持现有 fetch 全部行为
  },
  scheduled(controller, env, ctx) {
    ctx.waitUntil(runDatabaseMaintenance(env, controller.scheduledTime));
  }
};
```

不要在 `scheduled` 里调用公开 HTTP API，也不要把 D1 binding 转成 REST 请求。

### 4.2 每日过期 session 清理

新增内部函数：

```js
async function cleanupExpiredSessions(env, cutoffIso) {
  return env.MMC_DB.prepare(
    'DELETE FROM sessions WHERE expires_at <= ?'
  ).bind(cutoffIso).run();
}
```

要求：

- `cutoffIso` 使用 `new Date(scheduledTime || Date.now()).toISOString()`。
- 保留 `requireOptionalSession()` 中针对当前过期 Cookie 的即时单条删除；Cron 是兜底，不替换请求路径的安全检查。
- 删除必须有明确 `WHERE expires_at <= ?`，禁止无条件 DELETE。
- 日志记录 `deletedSessions`、截止时间、耗时和成功/失败状态，不记录 token、token hash、用户 ID 或 Cookie。
- 函数幂等；重复执行只会得到 0 条变化。

### 4.3 `last_seen_at` 30 分钟写入节流

在常量区新增：

```js
const SESSION_LAST_SEEN_WRITE_INTERVAL_MS = 30 * 60 * 1000;
```

修改 session 查询，增加：

```sql
s.last_seen_at
```

有效 session 处理逻辑：

1. 只读解析查询返回的 `last_seen_at`。
2. 若时间合法且距当前不足 30 分钟，不发出任何 UPDATE。
3. 若超过 30 分钟或时间异常，执行带并发保护的条件更新：

   ```sql
   UPDATE sessions
   SET last_seen_at = ?
   WHERE id = ?
     AND (last_seen_at IS NULL OR last_seen_at <= ?)
   ```

4. 第一个参数为当前 ISO 时间；第三个参数为当前时间减 30 分钟后的 ISO 截止值。

两层判断缺一不可：

- JavaScript 判断避免绝大多数请求连 UPDATE 语句都发出。
- SQL 截止条件避免同一 session 在边界时刻的并发请求同时修改同一行。

登录有效期仍固定为当前 `SESSION_TTL_DAYS = 14`，节流不能延长 `expires_at`，也不能把 session 改成滑动过期。

### 4.4 删除重复索引

新增 `schema/015_database_maintenance.sql`，其中包含：

```sql
DROP INDEX IF EXISTS idx_sessions_token_hash;
```

同时处理新库基线：

- 从 `schema/001_init.sql` 删除 `CREATE INDEX IF NOT EXISTS idx_sessions_token_hash ON sessions(token_hash);`。
- 保留 `token_hash TEXT NOT NULL UNIQUE`。
- 保留 `idx_sessions_user_id`。

原因：如果只在 015 中 DROP，但 001 仍创建，那么新库初始化和标准 migration chain 会先制造重复索引再删除；移除 001 中的显式定义可以让新库从一开始就正确。

删除索引后 D1 的 `database_size` 不一定立即下降，SQLite/D1 可能保留已分配页。这不构成失败。权威成功标准是：

1. `PRAGMA index_list('sessions')` 不再出现 `idx_sessions_token_hash`。
2. UNIQUE 自动索引仍在。
3. `EXPLAIN QUERY PLAN` 仍使用 `sqlite_autoindex_sessions_2 (token_hash=?)`。
4. 登录、session 恢复和登出行为正常。

### 4.5 月度增长记录

在 `schema/015_database_maintenance.sql` 新增极小的指标表：

```sql
CREATE TABLE IF NOT EXISTS database_monthly_metrics (
  month TEXT PRIMARY KEY,
  measured_at TEXT NOT NULL,
  database_size_bytes INTEGER NOT NULL,
  assets_count INTEGER NOT NULL,
  sessions_count INTEGER NOT NULL,
  expired_sessions_before_cleanup INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

迁移后业务表数量会从 24 增加到 25；每月仅一行，体积可忽略。

每日维护流程：

1. 先统计清理前过期 session 数量。
2. 删除过期 session。
3. 使用 `getLocalDateStringFromDate(date, 'Asia/Shanghai')` 判断上海日期。
4. 仅上海日期为每月 1 日时采集月度指标。
5. 使用 D1 查询结果的 `meta.size_after` 记录近似 `database_size_bytes`；同时查询 `COUNT(*) FROM assets` 和清理后的 `COUNT(*) FROM sessions`。
6. 以 `YYYY-MM` 为主键执行幂等 UPSERT。
7. 查询上一条月度记录，在 Worker structured log 中输出增长字节数和增长百分比。

月度预警条件：

- 本月比上月增加超过 `1,048,576 bytes`。
- 连续月增长比例超过 `20%`。
- 每日清理前过期 session 超过 `1,000`。

本轮只写结构化 `console.warn` 和 D1 指标记录，不新增邮件、Webhook 或公开管理 API。不要为了发送告警引入第三方服务和 secret。

建议日志形状：

```js
console.log(JSON.stringify({
  event: 'd1_maintenance',
  measuredAt,
  deletedSessions,
  expiredSessionsBeforeCleanup,
  monthlyMetricWritten,
  databaseSizeBytes,
  assetsCount,
  sessionsCount,
  alerts
}));
```

## 8. 回滚方案

### 8.1 代码/Cron 回滚

如果 scheduled handler 或 last-seen 节流出现代码故障：

1. 新增修复提交，移除/修正 `[triggers]` 和 scheduled 逻辑。
2. 重新 `npm run deploy`。
3. 不改写已推送历史，不 force push。

移除 Cron 时必须显式配置：

```toml
[triggers]
crons = []
```

因为配置缺失时 Wrangler 可能保留现有 trigger。

### 8.2 索引回滚

如果异常证据证明 token 查询没有使用自动索引，可单独恢复：

```sql
CREATE INDEX IF NOT EXISTS idx_sessions_token_hash ON sessions(token_hash);
```

正常情况下不需要恢复。

### 8.3 数据恢复

过期 session 删除属于可接受的身份数据清理，最坏影响只是对应旧会话重新登录。不要仅为了恢复过期登录状态执行整库 Time Travel。

只有发生误删未过期 session 或其他业务表被破坏时，才考虑：

1. 先停止 Cron/部署修复。
2. 确认备份 SQL、Time Travel bookmark 和故障时间。
3. 评估故障期间新增业务数据。
4. 经站长确认后执行恢复。

Time Travel restore 会覆盖当前数据库并取消进行中的查询，必须作为最后手段。
