# 架构说明

## 目标

解决你现在最痛的点:

- 很多人找你上架 / 下架时，手动改文件太繁琐
- 纯前端站没有账号体系，没有审核流
- 公告和站点说明也只能手工改脚本

所以这次的新项目把“内容管理”从静态文件维护，升级成后台驱动。

## 为什么不建议直接往旧目录硬塞后台

旧站的核心是：

- 人工维护首页和公告
- `build.py` 扫描目录
- 自动生成 `data.js`
- 自动生成所有分类页 HTML

这套结构很适合“站长一个人整理资源”，但不适合“多用户上传 + 审核 + 权限管理”。

如果继续往旧项目上叠账号和审核管理，会遇到几个问题：

1. 数据源会分裂：一部分在文件夹，一部分在数据库。
2. 分类页是脚本生成的，不利于权限和审核状态控制。
3. 文件上传、账号、审核日志本来就更适合后端系统。

所以更稳的做法是：

- 新建后台版项目
- 用 D1 管理结构化数据
- 用 R2 管理媒体文件
- 用 Worker 统一开放 API 和媒体访问
- 旧站资源逐步迁移过来

## 这次骨架里的数据模型

### users

- 注册用户
- 管理员
- 站长

### sessions

- 登录态 Cookie 对应的服务端会话

### folders

- 用户创建的文件夹
- 包含公开路径 slug
- 状态有 `draft / pending_review / published / rejected / offline`

### assets

- 文件夹下的图片 / 视频
- 文件存在 R2
- 数据库存文件名、类型、大小、排序、状态

### announcements

- 站内公告

### site_settings

- 首页公告主文案
- 弹窗标题、内容、按钮文案、跳转地址等

### review_logs

- 投稿
- 审核通过
- 驳回
- 下架

## 发布流

1. 用户注册 / 登录
2. 用户创建文件夹并上传图片、视频
3. Worker 把文件写入 R2 的 `pending/` 前缀
4. 数据库存一条 `folders` 记录和多条 `assets` 记录
5. 文件夹状态变成 `pending_review`
6. 管理员在后台审核
7. 审核通过后，文件夹状态改成 `published`
8. 前台首页自动展示，公开地址变成 `/${slug}`

## 和你的需求逐条对应

### 1. 用户注册 / 登录

已在 Worker 里做了账号注册、密码哈希、Cookie 会话。

### 2. 站长账号

当前骨架已支持角色：

- `user`
- `admin`
- `owner`

你最终只需要在数据库里把你的账号设成 `owner`，它就能：

- 删除其他用户
- 把用户升级为管理员

### 3. 用户上传文件夹

前端工作台已经提供：

- 文件夹名称
- 公开路径
- 文件夹简介
- 多文件上传

上传后自动进审核队列。

### 4. 审核通过后变成公开路径

当前公开路由就是：

- `https://域名/文件夹路径`

例如：

- `https://maomaochong.600318.xyz/搬波时间DLC`

## 还需要你后续确认或补的地方

### 1. 旧资源怎么迁

现在后台版支持“新投稿工作流”，但旧站有大量历史资源。

推荐后续补一个迁移脚本：

- 扫描旧目录
- 以“文件夹”为单位导入 D1
- 把原文件搬进 R2
- 给每个旧分类补一条 `published` 记录

这样能一次性把老站内容变成新站可管理内容。

### 2. 大视频上传

当前骨架走的是 Worker 直接接收上传，适合常见图片和中小视频。

如果后面出现更大的视频，建议再补一层：

- 浏览器直传 R2
- Worker 只负责签名和写元数据

### 3. 首个站长账号

当前骨架里，数据库中如果还没有 `owner`，那么首个注册的账号会自动成为站长。

所以部署后建议先由你自己注册第一个账号，再开放给其他人使用。

## 参考思路

你提到的 `flare-stack-blog` 给了一个有价值的方向：

- 用 Cloudflare 全家桶做轻量后台
- 把“管理页面”和“公开页面”放在同一站里

这次的骨架延续了这个思路，但把内容模型换成更适合“文件夹 + 图片 / 视频 + 审核”的结构，而不是博客文章模型。
