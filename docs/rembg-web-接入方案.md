# rembg-web 接入当前 Cloudflare Worker 项目方案

## 1. 目标

把 `rembg-web` 接入当前网站，提供一个“图片去背景/抠图”功能，并尽量保持现有项目架构不大改：

- 继续使用 Cloudflare Worker 作为统一入口
- 继续使用 `public/` 目录承载前端静态资源
- 尽量不把 AI 推理放到 Worker 端
- 优先在浏览器本地完成推理，再决定是否上传结果到 R2

本方案默认优先做“浏览器本地抠图 + 用户下载结果”的第一期，再预留“保存到站内资源库”的第二期能力。

## 2. 当前项目现状

当前项目的结构特点：

- Worker 入口：`src/worker.js`
- 静态资源目录：`public/`
- 前端是一个 `type="module"` 的原生单页应用，不依赖现成打包器
- 已经接入 D1、R2、静态资源分发
- 当前 Worker 对非 `/api/`、非 `/media/` 路径，直接走 `env.ASSETS.fetch(request)`

这意味着：

- 最适合接入的是“浏览器端 AI 推理”方案
- 不建议把 `rembg-web` 的模型推理逻辑放进 Worker
- 更合理的方式是新增一个前端页面或工具区，让浏览器直接运行 `rembg-web`

## 3. 为什么选 rembg-web

相对 `imgly/background-removal-js`，`rembg-web` 更适合当前项目做闭源商用方向的探索，主要原因：

- 代码许可证更友好，适合闭源商用评估
- 运行方式是浏览器端 ONNX Runtime Web，和你们当前静态前端更契合
- 支持自托管模型文件
- 不要求额外部署 Python 服务

需要注意：

- `rembg-web` 的代码许可证宽松，不等于所有模型文件天然都无额外限制
- 上线前仍应逐个确认最终选用模型的许可证和分发条件

## 4. 总体接入思路

建议分两期：

### 第一期：纯前端抠图工具

用户流程：

1. 进入 `/tools/remove-bg` 页面
2. 选择本地图片
3. 浏览器加载 ONNX Runtime 和模型文件
4. 在本地完成抠图
5. 页面展示前后对比
6. 用户下载 PNG 结果

这一期的优点：

- 不改现有数据模型
- 不增加 Worker 端推理负担
- 开发和上线风险最小
- 最容易先验证用户需求

### 第二期：抠图结果保存到站内

扩展流程：

1. 用户完成抠图后点击“保存到网站”
2. 前端把输出 PNG 作为 `File` 或 `Blob` 提交给 Worker
3. Worker 将结果写入 R2
4. D1 里记录该资源与用户、来源图、处理方式的关系
5. 结果可出现在用户后台或素材库中

## 5. 推荐技术方案

### 方案选择

推荐采用：

- `rembg-web` 在浏览器执行推理
- `onnxruntime-web` 作为推理运行时
- 模型文件托管在你们自己的站点静态目录中

不推荐：

- Worker 直接加载模型并执行推理
- 依赖第三方 CDN 在线加载模型作为正式生产方案

原因：

- Worker 环境不适合做大模型推理
- 浏览器本地推理更符合这个库的设计方向
- 自托管模型更稳定，也更方便控制版本

## 6. 与当前项目的最小改动边界

### 前端部分

建议新增：

- `public/tools/remove-bg.html` 或继续复用当前 SPA 路由
- `public/rembg-tool.js`
- `public/rembg-tool.css`
- `public/models/` 目录，用于放 ONNX 模型

在你们当前项目里，更建议继续复用现有 SPA，而不是单独做一个新 HTML。

建议做法：

- 在 `public/app.js` 中新增一个路由，例如 `/tools/remove-bg`
- 在当前导航中加入“AI 抠图”入口
- 用单独的渲染函数生成工具页面
- 用单独模块 `public/rembg-tool.js` 管理抠图逻辑

这样可以保持页面风格统一，也便于复用你们现有的登录态、Toast、上传交互等能力。

### Worker 部分

第一期几乎不需要新增 API。

可能需要的 Worker 改动只有：

- 为静态模型文件增加更长的缓存头
- 为工具页和相关脚本补充必要响应头
- 如果第二期要保存结果，则新增上传 API

## 7. 目录建议

建议最终目录形态如下：

```text
public/
  app.js
  styles.css
  rembg-tool.js
  rembg-tool.css
  models/
    u2netp.onnx
src/
  worker.js
docs/
  rembg-web-接入方案.md
```

第一期建议只放一个轻量模型：

- `u2netp.onnx`

原因：

- 文件小很多
- 首次加载更适合作为网站工具功能
- 能先验证体验和需求

如果后续用户确实在意质量，再考虑：

- `u2net`
- `u2net_human_seg`
- `isnet-general-use`

## 8. 模型托管策略

正式环境建议自托管模型，不要默认依赖远端下载。

推荐方式：

1. 把选定的模型文件放到 `public/models/`
2. 在前端初始化时显式指定模型路径
3. 路径示例：`/models/u2netp.onnx`

这样做的好处：

- 版本可控
- 避免第三方源失效
- 可利用 Cloudflare 静态缓存
- 更方便做国内访问优化

## 9. 前端接入设计

### 页面功能

第一期页面建议具备这些能力：

- 上传单张图片
- 显示原图预览
- 选择模型
- 点击开始抠图
- 展示处理进度和加载状态
- 展示透明背景结果
- 下载 PNG
- 重置任务

建议暂时不要第一期就做：

- 批量抠图
- 视频去背景
- 自动写入现有文件夹上传流程
- 服务端排队任务

### 页面交互建议

推荐使用两栏布局：

- 左侧原图
- 右侧抠图结果

页面状态建议包括：

- 未选择文件
- 正在加载模型
- 正在推理
- 推理完成
- 推理失败

错误信息建议区分：

- 模型加载失败
- 图片格式不支持
- 浏览器内存不足
- 推理超时或运行失败

## 10. 与现有上传系统的关系

你们当前上传系统是“文件夹 + 多文件上传 + 审核发布”模型，不是“图片工具”模型。

所以第一期不要把抠图强行塞进现有“新建文件夹上传”流程里。

更好的产品边界是：

- 抠图工具是一个独立页面
- 工具输出先提供下载
- 后面再决定是否接入“保存到我的资源”

如果第二期要和现有系统打通，建议新增一条清晰链路：

1. 用户在工具页完成抠图
2. 用户点击“保存到我的素材”
3. 前端上传结果文件
4. Worker 创建一个新素材记录，或者允许挂到指定 folder 下

这样比在现有表单中临时插一个“先抠图再传”更干净。

## 11. 性能与用户体验建议

### 模型选择

优先顺序建议：

1. `u2netp`
2. `u2net`
3. 视具体场景再增加专用模型

原因：

- `u2netp` 更适合做网页工具的首次加载
- 大模型虽然效果可能更好，但首次下载和内存压力更大

### 资源加载

建议：

- 首次只加载用户选择的模型
- 不要页面一打开就自动下载大模型
- 模型文件使用浏览器缓存和 Cloudflare CDN 缓存

### 图片尺寸控制

建议在前端做一层保护：

- 对超大图片做提示
- 必要时先压缩到合理尺寸再送入推理

理由：

- 浏览器端内存是主要瓶颈
- 对移动端尤其重要

可先设一个经验阈值，例如：

- 单图建议不超过 8MB
- 分辨率超过 4096px 的长边时提示用户压缩

## 12. Cloudflare Worker 需要补的能力

### 静态资源缓存策略

建议对模型文件设置更激进的缓存：

- `Cache-Control: public, max-age=31536000, immutable`

可以按路径判断：

- `/models/` 走长缓存
- 普通 HTML 保持现有策略

### 跨源隔离头

是否必须加：

- 不是所有场景都强制要求
- 但如果后续要追求更稳定的浏览器端推理能力，建议预留

建议评估的响应头：

- `Cross-Origin-Opener-Policy: same-origin`
- `Cross-Origin-Embedder-Policy: require-corp`

注意：

- 一旦开启跨源隔离，站内第三方脚本、字体、CDN 资源兼容性要重新检查
- 你们当前 `public/index.html` 依赖外部字体和 Font Awesome CDN，可能需要同步调整

所以我的建议是：

- 第一期先不强推跨源隔离
- 先按默认 WASM 路线验证功能
- 如果后面确实遇到兼容或性能瓶颈，再做第二轮响应头治理

## 13. 构建与依赖方案

这里有两个接法。

### 接法 A：继续保持无构建方案

做法：

- `public/index.html` 继续直接加载 `app.js`
- 在 `app.js` 内通过动态 `import()` 或 CDN ESM 引入 `rembg-web`

优点：

- 改动少
- 不需要马上引入 Vite

缺点：

- 第三方依赖管理比较脆弱
- 版本锁定和产物控制较弱

### 接法 B：给前端补一个轻量构建流程

做法：

- 引入 Vite 或 esbuild
- 把 `public/app.js` 挪到更清晰的源码目录
- 通过 npm 安装 `@bunnio/rembg-web` 和 `onnxruntime-web`

优点：

- 依赖更稳
- 更方便做代码拆分
- 更方便锁版本和后续扩展

缺点：

- 对当前项目结构改动更大

结合你们现在项目，我建议：

- 第一期先走接法 A，快速验证
- 如果功能验证通过，再考虑前端构建升级

## 14. 第一期开发表单

建议实际开发任务拆成下面这些点：

1. 新增 `/tools/remove-bg` 页面路由
2. 新增工具页 UI
3. 接入 `rembg-web`
4. 配置自托管模型路径
5. 实现上传、处理、预览、下载
6. 增加错误提示和加载态
7. 为 `/models/` 增加缓存头
8. 线上灰度验证桌面端和移动端体验

## 15. 第二期扩展方案

如果第一期反馈不错，再扩展：

### 方案 A：保存到个人素材

新增接口示意：

- `POST /api/tools/remove-bg/upload-result`

请求内容：

- 原图文件名
- 处理后 PNG 文件
- 可选 folderId
- 可选备注

Worker 处理：

- 校验登录态
- 将结果写入 R2
- D1 记录新素材

### 方案 B：作为上传前预处理步骤

在用户上传素材前，提供“先抠图再上传”的可选开关。

但我不建议第二期一上来就做这个，因为会让原有上传表单复杂很多。

## 16. 风险点

### 许可证风险

虽然 `rembg-web` 代码许可证更宽松，但最终生产使用的模型文件仍需逐项核验许可证。

### 浏览器性能风险

低端设备、旧手机、大图场景下，可能出现：

- 模型下载慢
- 推理耗时长
- 页面卡顿
- 内存不足

### 资源兼容风险

如果后续启用跨源隔离头，现有外部资源可能受影响，包括：

- CDN 字体
- 第三方样式
- 外部脚本

### 产品定位风险

如果一开始就和现有上传审核系统深度绑定，开发复杂度会明显升高。

## 17. 建议的落地顺序

最推荐的顺序是：

1. 用 `u2netp` 做一个纯前端工具页
2. 只支持单图、下载 PNG
3. 模型走自托管
4. 观察真实加载和推理体验
5. 再决定要不要接入“保存到网站”

## 18. 最终建议

对于你们当前项目，`rembg-web` 是可以接入的，而且接入方式应该是：

- 浏览器端推理
- Worker 继续只做静态资源和 API
- 第一阶段保持独立工具页
- 第二阶段再考虑接入现有 R2/D1 素材体系

如果让我给一个最务实的结论：

`rembg-web` 适合先做成网站里的一个“AI 工具页”，不适合第一步就改造成你们主上传流程的一部分。

这样最省改动，也最容易验证是否值得继续投入。
